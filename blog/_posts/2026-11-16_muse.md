###  Deploying Muse Spark Open (816B, NVFP4) on RunPod H200 with vLLM

<span style="color: red;">(Everything below this sentence is A.I. generated text.)</span>

**TL;DR:** 8×H200, the **NVFP4/modelopt** build, vLLM with `--moe-backend marlin` and `--reasoning-parser musespark1x`, set as the pod's **Container Start Command** (not launched by hand). 

---

#### 1. Hardware requirements

Muse Spark Open in NVFP4 is **~500 GB resident** (496 GiB checkpoint). The constraints:

| Requirement | Why |
|---|---|
| **≥ ~560 GB total VRAM** | The ~500 GB of weights plus KV cache and activation headroom. |
| **Hopper (SM90) or Blackwell (SM100)** | NVFP4 execution needs it. Ampere (A100/A40) **cannot** run these kernels. |
| **GPU count a power of 2** | Tensor-parallel must divide evenly. Use **4 or 8**. |
| **≥ ~550 GB free disk** | For the download itself. VRAM ≠ disk — you need both. |

Known-good and known-bad configurations:

| Config | Total VRAM | Result |
|---|---|---|
| **8×H200** | ~1,128 GB | ✅ Comfortable (this guide's reference) |
| 8×H100 | 640 GB | ✅ Works |
| 8×H100 NVL | 752 GB | ✅ Works |
| 4×B200 | 720 GB | ✅ Works |
| 4×H200 | ~564 GB | ⚠️ Works, but right at the edge — little KV headroom |
| **6×H100** | 480 GB | ❌ OOM — insufficient, and 6 isn't a power of 2 |

**Recommendation:** 8×H200 if you can get it. You get ~2× the model in VRAM, so `--gpu-memory-utilization 0.90` is relaxed and you have room for long contexts and real concurrency. 4×H200 technically fits but is tight enough that a tiny KV cache will throttle throughput.

#### 2. Get the *right* model build (this is a common trap)

There are multiple quantized builds of Muse Spark Open on Hugging Face. **vLLM's MuseSpark path requires the NVFP4 / NVIDIA ModelOpt build.** An Intel `inc` / MXFP4 build will load-fail or refuse — it is *not* interchangeable.

Pull the build whose `config.json` contains:
```json
"quantization_config": {
    "quant_algo": "NVFP4",
    "quant_method": "modelopt"
}
```

The repo is **gated**, so you need a Hugging Face account that's been granted access, plus a token. Newer images ship the **`hf`** CLI (not `huggingface-cli`):

```bash
hf auth login            # paste a READ token from an approved account; say "n" to git-credential
hf auth whoami           # confirms the token took

# Verify the build BEFORE committing to a ~500 GB pull — this fetches only config.json:
hf download <org>/Muse-Spark-Open-816B-A42B-NVFP4 config.json --local-dir /tmp/muse-check
grep -iE "quant_algo|quant_method" /tmp/muse-check/config.json
```

If that grep shows `NVFP4` / `modelopt`, you have the right repo. If it 404s, the repo id is wrong; if it says "requires approval," request access on the model page first.

**Download to a persistent volume**, not the container's overlay disk:
```bash
mkdir -p /workspace/models/muse-nvfp4
nohup hf download <org>/Muse-Spark-Open-816B-A42B-NVFP4 \
  --local-dir /workspace/models/muse-nvfp4 \
  > /workspace/muse_download.log 2>&1 &
# watch: du -sh /workspace/models/muse-nvfp4   (climbs toward ~500 GB)
```
On RunPod, `/workspace` is typically a network volume (FUSE/MooseFS). It's slower to read than local NVMe, but it **survives pod restarts** — which matters a lot, because you *will* restart the pod (see §4) and you do not want to re-download 500 GB each time. The FUSE filesystem disables auto-prefetch; `--safetensors-load-strategy=prefetch` on the serve command can speed subsequent loads if yours is crawling.

#### 3. Use a Muse-aware vLLM image

You need a vLLM build with Muse Spark support compiled in. Confirm it by checking for the model package and the reasoning parsers:
```bash
ls /usr/local/lib/python3.12/dist-packages/vllm/models/muse_spark/        # should exist
ls /usr/local/lib/python3.12/dist-packages/vllm/reasoning/ | grep muse    # muse_reasoning_parser.py, etc.
```
If `vllm/models/muse_spark/` is present, the architecture (`MuseSparkForConditionalGeneration`) is natively registered — so you do **not** need `--trust-remote-code`. These images use `python3` (not `python`).

> Note: Muse Spark is **multimodal** (there's a vision encoder). You can ignore that and serve it text-only — just don't send images.

---

#### 4. The RunPod gotcha that costs everyone an hour

RunPod vLLM templates **auto-start a default model** (e.g. Qwen3-8B) on port 8000 at `--gpu-memory-utilization 0.95`, which **hogs GPU 0**. Your `tp=8` launch then dies two ways:
- `OSError: [Errno 98] Address already in use` (port 8000 taken), and/or
- an OOM / imbalance on GPU 0 because the default server holds ~135 GB there.

**Do not try to kill it from the shell.** That default server is the container's *main process* (PID 1 is `docker-init`/tini running it). Killing it makes tini exit → the whole container restarts → RunPod's restart policy re-runs the same default command → you're back where you started. It's an infinite loop, and you'll waste money fighting it.

**The correct fix: replace what the container runs on boot.** Edit the pod's **Container Start Command** so it launches *Muse* instead of the default model, then restart.

- The entrypoint already supplies `vllm serve`, so the Start Command is **model-first** — it starts with the model path, *not* with `vllm serve`. (Mirror the form of whatever's currently in the field: if it begins with `vllm serve`, keep that prefix; if it begins with the model name, don't.)
- A **Restart keeps your GPU allocation.** Only a full **Stop/Terminate** releases the GPUs back to the pool (and you may not get scarce H200s back). We verified a restart retains all 8 GPUs.
- `sleep infinity` as a Start Command **does not work** — the entrypoint appends it to `vllm serve`, giving "unrecognized arguments."

Set the Container Start Command to the [serve args below](#5-the-serve-command), save, and **Restart** (not Stop).

#### 5. The serve command

For **8×H200 (Hopper)**, set this as the Container Start Command (model-first form):

```
/workspace/models/muse-nvfp4 \
  --served-model-name muse-spark-open \
  --tensor-parallel-size 8 \
  --moe-backend marlin \
  --reasoning-parser musespark1x \
  --max-model-len 32768 \
  --gpu-memory-utilization 0.90 \
  --host 0.0.0.0 \
  --port 8000
```

Flag-by-flag, because the two that matter most are non-obvious:

| Flag | Why it's there |
|---|---|
| `--tensor-parallel-size 8` | Shards across all 8 GPUs. **No** pipeline- or data-parallel — Marlin requires DP1/PCP1 (you'll see "MuseSpark1x Triton/Marlin currently requires DP1 and PCP1" if you violate it). |
| `--moe-backend marlin` | **Critical on Hopper.** The default MoE backend (HUMMING) is unsupported for Muse's NVFP4 MoE — you'll get `MuseSpark NVFP4 MoE requires FLASHINFER_TRTLLM or Marlin on Hopper; got HUMMING`. Marlin gives you W4A16 GEMMs with Triton finalization. On **Blackwell**, native NVFP4 paths work and you can drop this. |
| `--reasoning-parser musespark1x` | **Essential, and silently wrong without it.** Muse emits a channel format — `to=self<\|message\|>…reasoning…<\|eom\|>` for its analysis channel, `to=user` for the answer. Without the parser, the raw chain-of-thought (and the `to=self` markers) land in `content` and the actual answer may never surface. With it, `content` = the clean final answer and the CoT goes into a separate `reasoning` field. |
| *(no `--quantization`)* | Auto-detected from the config's `quantization_config` (modelopt NVFP4). Passing it is unnecessary. |
| *(no `--trust-remote-code`)* | The arch is natively registered in a Muse-aware image. |
| `--max-model-len 32768` | Muse is a **heavy reasoner** (~1,000+ reasoning tokens even for simple prompts), so give generations room. See §7. |
| `--gpu-memory-utilization 0.90` | Comfortable on 8×H200. On 4×H200 push to `0.95`. |

#### 6. Verify it's actually serving cleanly

The server loads ~500 GB from the volume (a few minutes), then captures CUDA graphs, then binds the port. Poll until healthy:
```bash
while ! curl -sf localhost:8000/health >/dev/null 2>&1; do echo "loading…"; sleep 15; done
curl -s localhost:8000/v1/models        # should list "muse-spark-open"
nvidia-smi                              # expect VLLM::Worker_TP0..7 across all 8 GPUs
```

**Then run a real smoke test — and use `max_tokens ≥ 2000`.** This is the step people get wrong: because Muse reasons so much, a 300-token request burns the whole budget *inside the reasoning channel* and returns empty/garbled content, making you think the parser is broken when it isn't.
```bash
curl -s localhost:8000/v1/chat/completions -H "Content-Type: application/json" -d '{
  "model":"muse-spark-open",
  "messages":[{"role":"user","content":"In one sentence, what is a YARA rule?"}],
  "max_tokens":2000
}'
```
**Success looks like:** `content` is a clean one-sentence answer with no `to=self` markers, and the chain-of-thought sits in a separate `reasoning` field, with `finish_reason: "stop"`. If `content` still contains `to=self…`, your reasoning parser isn't set (or isn't `musespark1x`).

#### 7. Accessing the endpoint & using it

vLLM serves an **OpenAI-compatible** API at `/v1`. RunPod exposes the HTTP port behind a proxy:
```
https://<pod-id>-8000.proxy.runpod.net/v1
```
No real API key is required; clients that demand one accept any dummy value. Example with the UK AISI **Inspect** framework:
```bash
OPENAI_API_KEY=dummy inspect eval your_task.py \
  --model openai/muse-spark-open \
  --model-base-url https://<pod-id>-8000.proxy.runpod.net/v1 \
  --max-tokens 32768
```
Two client-side notes:
- Use the framework's dedicated **base-URL flag** (`--model-base-url` in Inspect), not an ad-hoc `base_url` model-arg — passing it twice throws `got multiple values for keyword argument 'base_url'`.
- Don't set `OPENAI_BASE_URL` as a global env var or you'll silently reroute your *real* OpenAI calls to the pod.

**Heavy-reasoner budgeting:** across 371 mixed prompts, Muse averaged ~1,100 reasoning tokens/prompt and occasionally far more. At `--max-tokens 32768` it had zero truncations, but if you run tighter budgets, expect some prompts to hit the length cap *while still reasoning* (empty content, `finish_reason: length`) — handle those as "retry at higher tokens," not as refusals.

#### 8. Troubleshooting quick-reference

| Symptom | Cause | Fix |
|---|---|---|
| `quantization 'inc'` / MXFP4 errors on load | Wrong build | Use the **NVFP4/modelopt** repo (§2) |
| `MuseSpark NVFP4 MoE requires FLASHINFER_TRTLLM or Marlin on Hopper; got HUMMING` | Default MoE backend | Add `--moe-backend marlin` |
| `to=self…` chain-of-thought in `content` | No reasoning parser | Add `--reasoning-parser musespark1x` |
| Empty/garbled answer on a short request | `max_tokens` too small for a heavy reasoner | Use `max_tokens ≥ 2000` |
| `OSError: [Errno 98] Address already in use` | Template's default server on 8000 | Replace the **Container Start Command** (§4), restart |
| Killed the default server, it came back | It's the container's main process | Don't kill it — change the start command and restart |
| OOM on load | Insufficient VRAM (e.g. 6×H100) or util too high | Use ≥560 GB VRAM; on 4×H200 try `--gpu-memory-utilization 0.95` |
| `MuseSpark1x Triton/Marlin currently requires DP1 and PCP1` | Added data/pipeline parallelism | Use **tensor-parallel only** |
| `python: command not found` | Image uses `python3` | Use `python3` |
| `huggingface-cli: command not found` | Newer image | Use the `hf` CLI |
